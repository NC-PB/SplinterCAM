# AQ-026: Three gaps the CNC review found in the `ncx` slice: arcs that collapse at the machine's step, feeds that print as 0, unread messages outside `compile`

- Asked: 2026-10-27, plan 0007 step 6 (`ncx` implementation, lane F, cnc-reviewer round), by the coding agent (headless run)
- Box: 1 (Peter's judgement: machine safety, and REQ wording in a Reviewed SPEC)
- Question: three cases the Reviewed `src/splintercam/ncx/SPEC.md` does not cover, each a SPEC change if it is to be refused.
  1. **An arc that collapses at the machine's step.** REQ-NCX-016 refuses an arc whose end prints equal to its start at the NCX step, 0.000001 mm. An arc with a chord between about 0.000001 mm and the machine's step (0.001 mm on the shipped mills) passes, and NCXchange then rounds its start and end to the same point. On the machine: the control reads an arc whose end equals its start as a **full circle**, a 360° pass at the arc's radius, through the part. By D-149 and DEC-CL-006 this is NCXchange's to keep consistent, but NCXchange D363 is not implemented at the f74559c pin and nothing checks it today. `cl` refuses arcs only below eps_len, 0.000001 mm (REQ-CL-014). Options: (a) leave it to NCXchange (D-149) and simulate the compiled program before the dry run; (b) refuse in `ncx` any arc with |sweep| < 2π whose chord is below 0.001 mm (a constant until the machine's decimals reach the CAM, which D-148 keeps out of `ncx`); (c) ask NCXchange to refuse such arcs (T-039).
  2. **A feed or speed that prints as 0.** `cl` accepts any feed or speed above 0 (REQ-CL-017). One below 0.0000005 prints `F=0.0` or `RPM=0.0`. On the machine: what `F0` does is controller behaviour (a stop, an alarm or the last feed), and `ncx check` may or may not refuse it. Options: (a) refuse a printed 0 as `NCX_VALUE_OUT_OF_RANGE` (a REQ-NCX-010 change); (b) leave it to `model`, whose feed and speed ranges are far above it (plan 0007's job values are 300, 1200 and 8000).
  3. **A stderr line the parser cannot read, from `format` or `check`.** REQ-NCX-020 keeps it as `NCX_OUTPUT_UNREAD` (warning). For `compile` the implementation now fails the run on it (DEC-NCX-014 (e)). For `check --strict` and `format --check` an unreadable line with exit 0 still passes; `ncx` should exit 1 on any WARNING under `--strict` (research 27, Exit codes), so this only matters if the exit code and the text disagree. Options: (a) as implemented; (b) an unread line from any step is an error.
- Recommendation: 1 (a) for the slice plus (c), because the machine's step belongs to NCXchange (D-148, D-149) and Peter's dry run simulates the compiled program first; (b) if Peter wants a guard before D363 ships. 2 (b): `model`'s ranges already exclude it, and adding a writer rule for values nobody can enter costs a SPEC change. 3 (a): the exit code under `--strict` is the gate there. Safe defaults taken meanwhile: as the Reviewed SPEC says, with DEC-NCX-014 (e) and (f) failing `compile` closed. This pull request does not depend on the answers.
