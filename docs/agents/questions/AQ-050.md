# AQ-050: The point's register radius r in the NCX tool block

- Asked: 2026-11-08, plan 0007 (lane P: NCXchange 1e2fd00 and the point words of D-155), by the coding agent
- Box: 1 (Peter's judgement: an interface between modules, `cl` and `ncx`, and what the program tells the shop)
- Question: The tool block now carries the operation's point as `TOOL_POINT=k TIP_OFFSET=a POINT_RADIUS=r` (D-155). k and a come from the toolpath record (`ClHeader.point_number`, `axial_offset_mm`), but the record has no r: `src/splintercam/model/SPEC.md` holds `register_radius_mm` per point, and `src/splintercam/cl/SPEC.md` lists r as Later, with `comp` CONTROL. The writer therefore writes `POINT_RADIUS=0.0` for every point. On the machine, in the slice, nothing changes either way: compensation is off (`COMP=OFF`), the compilers write nothing for a and r (Peter's answer to NCXchange's drafts, 2026-10-02, item (d)), so the Fanuc, Siemens and Heidenhain programs are the same for r = 0 and r = 2. What differs is what NCX says: with a point whose register radius in the job is, say, 2 mm, the NCX file says 0, and NCXchange's VM, a later simulation or `ncx analyze`'s tool list (D-155: "so the VM, simulation and verification can place the tip and apply compensation") would show the setter a radius that is not what the job file asks to measure. Options: (a) as now: `POINT_RADIUS=0.0` until `comp` CONTROL comes, when r must reach the record anyway; the setup sheet and the job file are where the setter reads r. (b) carry r now: add `register_radius_mm` to `ClHeader` (`cl`), fill it in `strategies/profile` from the job's point, and write it; three modules, one more field, done in another lane. (c) refuse a point whose r is not 0 until (b): the writer cannot see r, so this would be a check in `job` or `model`, and it would refuse the default flat end mill point only if the user entered an r.
- Recommendation: (a) for the slice, and (b) with `comp` CONTROL (`src/splintercam/cl/SPEC.md`, Later), because with compensation off r has no effect on any axis and every module that would change for (b) is outside this lane. Safe default taken: (a), recorded as provisional in `src/splintercam/ncx/DECISIONS.md`, DEC-NCX-020 (c). The CNC review of 2026-11-08 found nothing unsafe in the motion with (a), but recommends (c) for the slice: `POINT_RADIUS=0.0` is a false statement whenever the job's point has r ≠ 0, which matters once a setter, `ncx analyze` or a simulation reads it. The point comment of REQ-NCX-029 (AQ-051) does not name r for that reason.
- Status: Answered 2026-10-27
- Answer: write the job's r (Peter, 2026-11-08): the record carries the point's register radius (ClHeader gains it, job fills it from the model's point) so NCX states POINT_RADIUS truly; compensation stays off.
