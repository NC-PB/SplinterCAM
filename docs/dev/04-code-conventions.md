# 04. Code conventions

Two readers matter: the person who reviews and maintains the code, and the next agent that has to change it. Both need the same things: plain structure, honest names, and the reason behind every non-obvious line. Formatting is never discussed: the formatter decides.

## Readability first

- Write the obvious version. Clever generic code, reflection and metaprogramming are allowed only where an ADR says why.
- Prefer plain data types and functions over deep class hierarchies. Composition over inheritance.
- Small functions (about 60 lines at most; the checked limits are in [12](12-lean-code.md), section 3), one level of abstraction per function, early returns instead of deep nesting.
- Write only what a requirement needs: no options, parameters or extension points nobody asked for. A helper, class or wrapper is created when a second caller exists, not before ([12](12-lean-code.md), section 2).
- Library before own code: use what Clipper2, NumPy, OCCT or the standard library already do.
- Follow the pattern of the nearest existing module. If the pattern is wrong, fix it everywhere in a separate change, not in one place.
- Names come from [the glossary](../glossary.md): `stepover`, `allowance`, `engagement_angle`, not synonyms. The glossary gives the exact code spelling.

## Units, numbers and tolerances

- Internally: millimetres and radians, as `double` (64-bit). Degrees appear only in the UI, in files meant for people and in G-code ([RESEARCH 01](../research/01-foundations.md)).
- Use unit-carrying types where the language makes them cheap; otherwise a name suffix: `feed_mm_per_min`, `angle_rad`, `speed_rpm`. A bare `double` parameter without unit in its name or type is a review failure.
- Never write a literal epsilon. Tolerances come from the `ToleranceSet` in the `Context` (`length_eps`, `angle_eps`, `chord_tol`, the stage shares). Comparisons go through helpers such as `nearly_equal(a, b, tol)`.
- No magic numbers. Every constant is named, in one place per module, with a comment giving its source: a RESEARCH section, a paper or a tool maker's document.
- No values buried in code (D-049). Tolerances, thresholds, step limits, weights and other tuning values are declared parameters with unit, default, range and source, kept in the operation's parameter declaration or in the documented defaults file, so users and agents find and change them without reading algorithm code. Only mathematical constants and numeric guards stay in code.

## Comments and documentation

- Comments explain **why** and **where from**, not what the next line does:

```text
// Uncut corner condition s <= R(1 + sin(beta/2)): RESEARCH 04 "Uncut corners"; Held 1991.
// Retry with a slightly different distance near critical offsets: RESEARCH 18, 2D item 6.
```

- Every public function and type has a doc comment with units, preconditions, postconditions and the requirement IDs it implements. Private functions get no docstring, and a comment only where the reason is not obvious. Comments never restate the code or the SPEC.
- A `TODO` must reference an issue or plan ID (`TODO(#123)`); a lint rejects bare TODOs.
- Generated code starts with `Generated by <tool> from <source>. Do not edit.` and lives in a `generated/` subfolder.
- Every source file starts with `SPDX-License-Identifier: Apache-2.0` and a one-line purpose.

## Errors and diagnostics

- Validate at the boundary, trust inside. Public functions, importers and kernel entry points check their inputs; code inside a module does not re-check what the boundary guarantees.
- Expected outcomes are values: an empty offset, a tool that does not fit, a hole that cannot be reached. Return them as results with typed diagnostics ([03](03-architecture-rules.md)).
- Programming errors (a broken invariant, a null where none is allowed) fail loudly with an assertion or exception. Assertions stay on in release test builds.
- Never swallow an error. Never catch "everything" except at the top of a job, where the failure is logged, dumped for replay and reported ([RESEARCH 18](../research/18-known-pitfalls.md#general-engineering)).
- Never swallow out-of-memory or cancellation.

## Determinism

- Stable sorts, with an explicit tie-breaker.
- Never let the output order depend on hash-map iteration, pointer addresses or thread timing.
- Random numbers only from a seeded generator passed in through the `Context`.
- Text output (G-code, reports) formats numbers with an invariant culture and explicit rounding rules ([RESEARCH 18](../research/18-known-pitfalls.md#multi-axis-machine-and-post-processing), item 1).

## State and concurrency

- No global mutable state, no singletons holding data. Caches belong to the job and are keyed by geometry hash.
- Every long computation takes the cancellation token and reports progress; it checks for cancellation at least every few hundred milliseconds of work.
- Parallel code gets per-thread scratch data and merges in a fixed order.

## Logging

- Structured logs with the operation ID; no printing to the console below layer 6.
- Log decisions a person would want to know about (a retry, a fallback, a skipped region) at info level, with the diagnostic code.

## Tests (details in [06](06-testing-and-quality-gates.md))

- Tests carry the requirement ID as a pytest marker, `@pytest.mark.req("REQ-OFF-003")`, and a name that says what they check: `test_inward_offset_stays_inside_region`.
- Geometry is compared with tolerances or a Hausdorff distance, never as exact floats or text.

## Language appendix ([ADR 0004](../decisions/0004-tech-stack.md))

### Python

- One pinned CPython version (3.13 to start); environments and the lock file are managed with uv. `src/` layout, one package: `splintercam`.
- ruff for linting and formatting (line length 100), including the function limits of [12](12-lean-code.md) (`C901`, `PLR0911` to `PLR0915`) and unused arguments (`ARG`); pyright in strict mode. Both run in `tools/check`. A `# type: ignore` needs its reason on the same line.
- Type hints on every function. `Any` appears only at the OCP boundary inside `io`, `features` and `apps/desktop`, never in a public signature.
- Value types are frozen dataclasses with slots (`@dataclass(frozen=True, slots=True)`); interfaces are `typing.Protocol`; fixed choices are `enum.Enum`.
- Arrays are `numpy.typing.NDArray[numpy.float64]` (or an integer type for indices); the docstring states shape and units, for example "(n, 2) points in mm".
- Units: name suffixes (`feed_mm_per_min`, `angle_rad`) or `NewType` aliases (`Mm`, `Rad`); one choice per module.
- Names: `snake_case` for functions and variables, `PascalCase` for classes, `UPPER_CASE` for constants; glossary terms in their code spelling.
- Public API: an explicit `__all__` in each module's `__init__.py`; internal modules and names start with an underscore.
- Expected outcomes return the `Result` type from `foundation` with diagnostics; exceptions only for programming errors.
- No per-point Python loops in code that runs on real parts: vectorise with NumPy or move the loop into a kernel. Benchmarks guard the hot paths.
- Long OCCT operations run in a worker process (D-140: OCP holds the interpreter lock for the whole of every OCCT call); kernels can run in threads because they release the interpreter lock.
- Tests: pytest; property tests with Hypothesis.

### C++ kernels

- C++20 plus `std::expected` (supported by current MSVC, GCC, Clang and Apple Clang). No C++20 modules yet: CMake does not support them with Apple Clang.
- One `kernel/` folder per module; namespace `SplinterCAM::<module>`; `bindings.cpp` is the only file that includes nanobind.
- No `new` or `delete`, no owning raw pointers: RAII and value types, `std::span` for views into arrays, `std::vector` for owned data.
- Expected failures return `std::expected<T, KernelError>`; the binding turns them into diagnostics. No exception leaves a kernel.
- No OCCT, Qt or Python headers. C++ libraries only from the list in `architecture/modules.yaml`, fetched at pinned versions.
- clang-format for formatting. Warnings are errors (`-Wall -Wextra -Wpedantic -Werror`, `/W4 /WX` on MSVC). clang-tidy with the `bugprone-*`, `cppcoreguidelines-*`, `performance-*` and selected `modernize-*` checks, plus `readability-function-size` and `readability-function-cognitive-complexity` with the limits of [12](12-lean-code.md).
- CI builds the kernels a second time with AddressSanitizer and UndefinedBehaviorSanitizer and runs the whole pytest suite against that build. Standard-library hardening (`_GLIBCXX_ASSERTIONS`, the libc++ hardening mode) is on in test builds.
- Determinism as everywhere: no output order from unordered containers, fixed merge order after parallel work.
- Kernels are tested through their module's Python API. C++-only unit tests (Catch2) are added only for internals the API cannot reach.
